# Multi-Node Execution Protocol

The protocol between execution leases, tenant tool relays and tool calls that lets `hensu-server` run as several active nodes behind an ordinary load balancer.

Fixed constraints: Decision 3 stands (the server opens no outbound connections; tenants connect in); Postgres is the only shared infrastructure; `hensu-core` stays dependency-free; native-image rules apply; the fault-injection test's dependencies never reach the runtime classpath. Tenant binding, request ownership and catalog invalidation are fixed requirements of the relay contract (section 3.1).

**Summary.**

- Ownership that follows a connection cannot be made correct: a tool call bound to a stream one node holds needs tenant affinity, and a lease judged by heartbeat age against node clocks and fenced only at checkpoints lets a stale run keep calling tools and a skewed clock steal a live execution (section 2).
- The chosen protocol is a journaled relay pull (section 3): claims fenced by an epoch in every statement and expired by the database clock; a journal of model turns and nested-flow checkpoints so a recovered run replays rather than re-decides; tool calls as durable intents that the tenant's relay pulls from any node and acknowledges before executing, so each runs at most once; idempotent starts. Decision 3 is unchanged – the server still opens no connection to a tenant.
- TLC finds no violation of S1, S2, S3, S3a, S5 or S6 in the protocol's model, exhaustively within its bounds: one execution under every fault, and two executions sharing the relay under each half of the fault set, on two nodes with one clock skewed (section 4). The fault-injection test runs 611 executions through crashes, pauses, partitions, a deploy, skew and 293 dropped responses with no safety or liveness finding (section 5).
- The change removes the split-pipe gateway, node-id leases, the heartbeat job and the recovery sweep, and adds three tables, a four-request relay protocol and the journal seam in `hensu-core`. It is deployed with a one-time stop-and-start cutover (section 6).

### Faults

Any fault may strike at any step, repeatedly and in combination.

- **F1 Node crash.** The process dies with its runs, connections and in-memory state. Peers see its connections reset – or, when the host dies, hang until a timeout fires.
- **F2 Pause.** The whole process stops – GC, `docker pause`, VM freeze – for longer than any lease, then resumes with its memory intact and no knowledge that it stopped. Its connections stay open. A pause can fall between a check and the action it guards.
- **F3 Node–DB partition.** A node cannot reach Postgres while its HTTP traffic keeps working, and later heals. A full DB outage is F3 on every node.
- **F4 Relay reconnect.** A relay's connection drops (network, LB idle timeout, relay restart) and the relay reconnects through the LB to any node, including the one it left. The old connection may linger half-open on either end.
- **F5 LB misrouting and rebalance.** Any single request – connect, answer, start, resume, poll – reaches any live node; a long-lived connection may be cut and re-established elsewhere.
- **F6 Rolling deploy.** Nodes stop one at a time (SIGTERM, 30 s drain, SIGKILL) and are replaced, old and new versions running side by side. A replacement may reuse its predecessor's node id (a StatefulSet pod name, a configured `hensu.node.id`), and a paused predecessor may still be alive when it does.
- **F7 Clock skew.** Node wall clocks differ from each other and from the DB clock by any offset and may step. The DB clock is monotone except across a primary failover, where it may step by the DB hosts' NTP bound.
- **F8 Delay, duplication, reordering.** A request or answer may be held arbitrarily long – in a proxy, a socket buffer, or by an F2 of its sender – and may be delivered twice.

Out of scope: Byzantine nodes; a relay acting against its own tenant; Postgres losing committed writes or breaking row-level serialization.

### Delivery Semantics of a Tool Call

**Exactly-once decisions, at-most-once execution, and an explicit "outcome unknown".**

The engine checkpoints before each node, and a node attempt makes up to `maxToolCalls` tool calls and one more model call than that before the next checkpoint. Re-running a node attempt from its checkpoint therefore repeats tool calls whose effects already happened, and, because the model is not deterministic, may decide differently and leave the earlier calls as orphans that no durable history mentions. The protocol removes both:

- Every non-deterministic step of a node attempt that can call tools – the model's turn, the outcome of each call – is recorded in Postgres under the run's claim before the run acts on it. A recovered run replays the journal: recorded model turns are not requested again, recorded outcomes are not delivered again, and the run reaches the first unrecorded step having made exactly the decisions the original run made.
- A tool call exists for the relay only as an *intent*: a journal record committed under the claim before any relay can see it. The relay may be *offered* an intent more than once, but executes it only after acknowledging it, and exactly one acknowledgement can succeed. An intent therefore runs once or not at all, whichever claim or node is involved.
- Each intent carries a key, `(tenant, execution, position, sequence)`: the node visit and branch path of the attempt, and the call's index within it. Replay is deterministic, so a recovered run reproduces every key and finds the original intent instead of creating a second one; two different calls never share a key. The key is also what a relay de-duplicates on across its own restarts, and what correlates audit records across claims.
- A start is a request too, and F8 applies to it: a client that lost the answer retries, and the retry may reach another node. A start carries an idempotency key; the first start with a key creates the execution, and every later start with the same key and request returns that execution and creates nothing.
- An intent has exactly one outcome once settled, and the first one recorded wins. An acknowledged call that does not complete within its deadline is recorded as `TIMEOUT`, meaning *outcome unknown*: the call may have run. An intent no relay acknowledged within its dispatch deadline is recorded as `UNAVAILABLE`, meaning *it did not run*. Both records are final, so replay reproduces them.

### Invariants

A *claim* is one acquisition of an execution's lease by one run. An execution's claims carry strictly increasing *epochs*. An *effect* is a committed write to the execution's state or journal, or a tool request the relay executes. *DB time* is Postgres `now()`. Every invariant is stated over observable histories – claims, writes and intents in the DB; deliveries received and executed by the relay, each with epoch, key and node; outcomes handed to the agent – so the TLA+ properties in section 4 and the fault-injection test's checker in section 5 assert these IDs as written.

#### Safety

These hold in every reachable state under any combination of F1–F8.

- **S1 One run per claim.** An execution has at most one claim at any DB instant, and at most one run – on any node, its own included – acts under that claim.
- **S2 Fenced state.** A write to an execution's state or journal commits only under its current claim, terminal writes included. The durable history is one chain of claims, never an interleaving of two runs.
- **S3 No unjournaled effect.** The relay executes only requests that were committed as intents under the claim current at commit time, and a superseded claim commits no further intent. A stale run cannot cause a call the journal does not contain.
- **S3a At-most-once execution.** The relay executes each intent at most once, across offers, nodes and claims.
- **S4 Journal before act.** A run delivers a call only after its intent has committed, consumes an outcome only after it has committed, and acts on a model turn only after it has committed. A run that cannot write the journal makes no further calls.
- **S5 No live steal.** A claim whose holder renewed it within the lease period, measured in DB time, is never superseded, whatever any node clock reads. S1–S4 do not rely on S5; S5 keeps skew from turning healthy runs into aborted ones.
- **S6 Outcome integrity.** An intent has at most one outcome; only its own tenant's relay can supply it; and a run consumes only outcomes of its own execution's intents.
- **S7 Replay fidelity.** Every delivery of a key carries the same tool name and arguments, and a recovered run consumes, for each journaled step, exactly what the original run recorded.
- **S8 Idempotent start.** Starts carrying the same idempotency key create at most one execution, whichever nodes they reach and however they interleave; a different request reusing the key is refused rather than answered with an execution it did not start.

#### Liveness

These hold under fairness: pauses and partitions end, and eventually some node reaches the DB while the tenant's relay can reach some node.

- **L1 No stranding.** Every execution that is neither paused for review nor terminal eventually advances past its next step or terminates. No lease is renewed for a run that no longer exists, no claim ping-pongs between nodes, and no row waits on a particular node to clear it.
- **L2 Bounded recovery.** After an F1, each of the dead node's executions resumes elsewhere within the lease period plus the pickup latency.
- **L3 Routing independence.** Under an ordinary LB, no request is refused, answered 404 or left to time out because of the node it reached. A start or resume accepted by any node is executed, and an answer sent to any node reaches the run awaiting it. The one exception is a node that cannot reach Postgres (F3): it cannot serve anything, so it reports not-ready and answers 503 with `Retry-After` rather than accepting work it cannot record; an LB that health-checks routes around it, and the client's retry lands elsewhere. The fault-injection test counts these 503s separately and does not score them as L3 violations.
- **L4 Routing faults are not tool outcomes.** F4–F6 never reach the agent as a tool result. Only the relay's answer, a `TIMEOUT` for a delivered call, or an `UNAVAILABLE` for a call no relay ever took within its dispatch deadline, reaches the agent.
- **L5 Graceful drain.** A node told to stop hands every execution it runs to the cluster within the drain window, and each resumes elsewhere without failing, without waiting out a lease, and without re-delivering a call.

## 2. Why Connection-Bound Ownership Fails

The direct way to run several nodes is to let each node own what it runs: an execution's lease names the node, a heartbeat keeps it, a sweep takes it over once the heartbeat has aged, and a tool call travels down the stream of whichever node the tenant's relay is connected to. Each of those choices breaks an invariant of section 1 under a fault it is meant to survive.

- **A lease judged by heartbeat age against node clocks** breaks S5: a node whose clock runs ahead (F7) finds a heartbeat written a moment ago stale and takes over a live execution. A lease that names a node id breaks S1 and S2 as soon as a replacement reuses the id of a predecessor that is only paused (F6 with F2): both processes pass a fence on the node id.
- **A fence checked only at checkpoints** breaks S3 and S4: a run paused or partitioned between two checkpoints (F2, F3) wakes after another node has taken the execution over and keeps calling tools until its next checkpoint, and a run that cannot reach Postgres keeps calling tools with no durable progress.
- **Re-running a node attempt from its checkpoint** breaks S7 and the delivery semantics: the model is asked again and may decide differently, and calls that already ran are sent again under new request ids that the relay cannot de-duplicate (F1).
- **A tool call bound to a stream one node holds** breaks L3 and L4 under an ordinary load balancer: an answer, a start or a resume that reaches another node has nowhere to go (F5), and a relay that reconnects elsewhere (F4, F6) leaves every execution on the old node calling a stream that is gone. Tenant affinity at the load balancer narrows the window without closing it, because the stream moves on every reconnect and every deploy.
- **A start that creates an execution per request** breaks S8: a client that retries after a lost answer (F8) runs the workflow twice.

Section 3 removes each of these premises rather than patching it.

## 3. Candidate Protocols

### Sources

- PostgreSQL `NOTIFY` (<https://www.postgresql.org/docs/current/sql-notify.html>): "if a `NOTIFY` is executed inside a transaction, the notify events are not delivered until and unless the transaction is committed"; "messages from different transactions are delivered in the order in which the transactions committed"; "If this queue becomes full, transactions calling `NOTIFY` will fail at commit"; payload "must be shorter than 8000 bytes".
- PostgreSQL `LISTEN` (<https://www.postgresql.org/docs/current/sql-listen.html>): "`LISTEN` takes effect at transaction commit"; "all the sessions currently listening on that notification channel are notified"; and the rule "first execute (and commit!) that command, then in a new transaction inspect the database state as needed by the application logic, then rely on notifications to find out about subsequent changes". A session that is not listening receives nothing for that period: notifications are a wake-up signal, never the record.
- PostgreSQL `src/backend/commands/async.c`, `PreCommit_Notify`: "Serialize writers by acquiring a special lock that we hold till after commit. This ensures that queue entries appear in commit order". Notifying commits are serialized cluster-wide, so a notification per tool call is affordable at 300/s but is not free.
- Temporal matching service, `service/matching/matching_engine.go`: `AddActivityTask` "either delivers task directly to waiting poller or save it into task queue persistence"; `PollActivityTaskQueue` returns an empty response when the long poll times out, and drops a matched task when history answers `TaskAlreadyStarted` ("Duplicated activity task") or `NotFound`. History's `IsActivityTaskNotFoundForToken` (`service/history/api/activity_util.go`) rejects a completion whose token attempt differs from the activity's (`token.Attempt != ai.Attempt`), and `respondactivitytaskcompleted/api.go` answers `ErrActivityTaskNotFound`. The pattern: tasks are durable, a poller is matched to a task by the server, starting is recorded before the worker runs it, and a stale token cannot complete it.
- AWS Step Functions, `GetActivityTask` (<https://docs.aws.amazon.com/step-functions/latest/apireference/API_GetActivityTask.html>): "This initiates a long poll … The maximum time the service holds on to the request before responding is 60 seconds"; workers "should set their client side socket timeout to at least 65 seconds". The best-practices guide (<https://docs.aws.amazon.com/step-functions/latest/dg/bp-activity-pollers.html>): "The `GetActivityTask` API is designed to provide a `taskToken` *exactly once*. If a `taskToken` is dropped while communicating with an activity worker, a number of `GetActivityTask` requests can be blocked for 60 seconds". `SendTaskHeartbeat` (<https://docs.aws.amazon.com/step-functions/latest/apireference/API_SendTaskHeartbeat.html>) answers `TaskTimedOut` when "The task token has either expired or the task associated with the token has already been closed". A pull protocol must therefore say what happens to a task whose poll response is lost.
- Kleppmann, *How to do distributed locking* (<https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html>): "if the GC pause lasts longer than the lease expiry period, and the client doesn't realise that it has expired, it may go ahead and make some unsafe change"; "a fencing token is simply a number that increases … every time a client acquires the lock"; the storage "rejects the request with token 33" once it has seen 34; and timeouts may only be relied on for liveness, since safety would need "bounded network delay", "bounded process pauses" and "bounded clock error".

### What Each Candidate Must Carry Regardless

Four mechanisms appear in every candidate that is to hold S1–S8, because their invariants do not depend on the transport:

- **A per-claim epoch, compared only in Postgres.** Every claim increments `claim_epoch`; every write to an execution's state or journal carries the epoch in its `WHERE` clause and commits in one statement (S1, S2). Lease expiry is written and compared with `now()` alone (S5). Renewal is per claim, so a run that no longer exists stops renewing (L1), and a node id is only a label that a replacement may reuse without inheriting anything.
- **The step journal.** Model turns and tool intents are committed under the epoch before the run acts on them (S3, S4); a recovered run replays them (S7). Without it no candidate holds S3 or S7: re-running an attempt repeats its calls under any transport.
- **An explicit execution state machine** – `RUNNING(epoch, owner, expires_at)`, `RUNNABLE`, `PAUSED`, `DONE` – instead of a state inferred from a nullable owner, so that drain (L5) has a state to hand executions to and every transition is one conditional statement.
- **An idempotency key on start**, checked by the insert that creates the execution (S8). Without it, a start retried after a lost answer runs twice under any transport.

The candidates differ in how a committed intent reaches the relay and how its answer reaches the run.

(a) fails L3 and L4 by construction: the answer to a pushed request can only be consumed on the node that pushed it, and an ordinary LB does not send it there. Making any node able to accept the answer means storing it in Postgres, which is (b). (b) and (c) both hold every invariant once they carry the shared mechanisms; they differ in where the connection state lives. (b) keeps a long-lived stream per tenant pinned to one node, and with it supersede, keepalive, half-open detection and a re-push rule for every reconnect – the connection state behind the failures of section 2. (c) has no server-held connection: each poll is independent, every piece of protocol state is a row, and any node can serve any request.

### Recommendation: (c), Journaled Relay Pull

(c) is the pattern every system cited above uses for workers that must connect in – Temporal's activity task queues and Step Functions activities – and it is the only candidate whose correctness does not depend on which node holds a connection. Its one structural weakness, named by Step Functions itself – a task whose poll response is lost waits for its timeout – is closed by separating *offer* from *start*: a poll offers tasks under single-use tokens, the relay acknowledges a token before it executes, and an offer that is not acknowledged within the ack deadline (10 s) is withdrawn and offered again under a new token. Because a token can be acknowledged only while its offer is current, exactly one acknowledgement succeeds per intent, which upgrades the delivery semantics from at-least-once to **at-most-once execution**: an intent runs once or not at all, and an acknowledged call that does not complete within its deadline is recorded as `TIMEOUT` – outcome unknown – rather than delivered a second time.

The added latency (≈ 12–25 ms) is inside the 50 ms budget, and the `NOTIFY` commit lock costs two notifying commits per call – about 600/s at peak.

The full protocol is specified in section 3.1 and modelled in section 4.

### 3.1 The Journaled Pull Protocol

#### Execution State Machine

Columns of `runtime.execution_states` replace `server_node_id` and `last_heartbeat_at`: `run_state`, `claim_epoch`, `claim_owner` (a label for operators, never compared), `claim_expires_at`, and `step` – the main-flow step counter that names journal positions.

| Transition                                  | Statement (all compare `now()` only)                                                                                                                                                                                                                                                  | Invariant      |
|---------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------|
| start → `RUNNING(1, me)`                    | `INSERT` with `claim_expires_at = now() + ttl`, and with the client's `start_key` and request digest `ON CONFLICT (tenant_id, start_key) DO NOTHING`; a conflict returns the execution that holds the key                                                                             | S1, S8         |
| renew                                       | `UPDATE … SET claim_expires_at = now() + ttl WHERE (execution, claim_epoch) IN (my live claims) AND run_state = 'RUNNING'`; a claim not returned is lost and its run is preempted; a node that cannot renew for a TTL preempts all its runs                                           | S5, L1         |
| checkpoint, journal write, intent insert    | conditional on `claim_epoch = e AND run_state = 'RUNNING'` in the same statement – an `UPDATE`'s `WHERE`, or for an insert a `FOR SHARE` read of the execution row in the statement's CTE, so no pickup can commit between the check and the insert; 0 rows → `RunPreemptedException` | S2, S3, S4     |
| expire or drain pickup → `RUNNING(e+1, me)` | `UPDATE … SET claim_epoch = claim_epoch + 1 … WHERE (run_state = 'RUNNING' AND claim_expires_at <= now()) OR run_state = 'RUNNABLE'` with `FOR UPDATE SKIP LOCKED`, released executions first                                                                                         | S1, S5, L1, L2 |
| resume after review → `RUNNING(e+1, me)`    | `UPDATE … WHERE run_state = 'PAUSED'`                                                                                                                                                                                                                                                 | S1, L3         |
| pause → `PAUSED`, finish → `DONE`           | conditional on `claim_epoch = e`; clears owner and expiry                                                                                                                                                                                                                             | S2             |
| drain → `RUNNABLE`                          | conditional on `claim_epoch = e`, then `NOTIFY`                                                                                                                                                                                                                                       | L5             |

Claim TTL 30 s, renewal every 10 s, pickup sweep every 5 s plus a `NOTIFY` on every `RUNNABLE` transition: L2 ≤ 35 s plus replay.

#### Step Journal

A *position* names a node attempt: the nested-flow scope (empty for the main flow; `<position>/f:<target>/` for a fork branch, `/p:<branch>/` for a parallel branch, `/w:<node>/` for a sub-workflow) followed by the flow's step counter. Positions are unique within an execution and reproduced exactly by a replay.

- `runtime.execution_journal(tenant_id, execution_id, main_step, position, kind, idx, payload)` holds two kinds of record. `turn` records are model turns keyed by position and turn index – turn 0 is the opening conversation, turn *i* the model's *i*-th answer – inserted under the epoch fence before the session acts on them. `flow` records are the latest checkpoint of each nested flow, keyed by its scope, because a nested flow has no execution row of its own and a fork has several cursors. `main_step` is the main-flow step a record belongs to: a main-flow checkpoint at step *s* deletes every record below *s* in the same statement, and settling the execution deletes the journal.
- `runtime.tool_intents(id, tenant_id, execution_id, call_key, tool_name, arguments, arguments_digest, state, created_epoch, created_at, dispatch_deadline_at, offer_token, offer_expires_at, deadline_at, outcome_status, outcome, settled_at)` holds tool calls, keyed `position#sequence` within the execution. An intent is inserted under the epoch fence with `ON CONFLICT (tenant_id, execution_id, call_key) DO NOTHING`, so a replay finds the original. A replayed call whose tool name or argument digest (SHA-256 of the canonical JSON) differs from the stored one is a replay divergence and fails the execution (S7); the digest survives the arguments being cleared.
- Intent states: `PENDING → OFFERED(token, ack deadline) → STARTED(call deadline) → DONE(outcome)`; `OFFERED → PENDING` when the ack deadline passes; `PENDING → DONE(UNAVAILABLE)` at the dispatch deadline (5 min); `STARTED → DONE(TIMEOUT)` at the call deadline (60 s); `PENDING` or `OFFERED` → `CANCELLED` when the execution finishes. `STARTED` is never cancelled: the relay may be running the call, and only its outcome or the call deadline may settle it. Every transition is one conditional statement compared against `now()`; the three deadline transitions run in one statement every second and notify the waiting runs in it.
- Arguments are cleared when an intent settles; the redacted copy in `tool_audit` – keyed by the call's execution-qualified id, so a replayed call is recorded once – is the record. While a call is open its arguments are in Postgres unredacted, parameters declared `sensitive` included, because the relay needs them. The database is therefore inside the trust boundary for open calls, as it already is for execution contexts.
- Retention follows the execution: journal records are deleted as the main flow checkpoints past them and when the execution settles. Settling also clears the outcomes of the execution's settled intents in the same statement – only a replay of the call's own attempt reads an outcome, no attempt is replayed past a settle, and `tool_audit` keeps the result. Intent rows (key, tool, digest, status) and catalogs are kept, intents until their execution row is deleted (`ON DELETE CASCADE`). The server has no execution retention policy yet ([`docs/tickets/execution-retention-policy.md`](tickets/execution-retention-policy.md)); one removes an execution's intents with it.

#### Relay Contract (`/mcp/v1`)

| Request                                                          | Effect                                                                                                                                                                                                                          | Answers                                                                                                                                                                                                              |
|------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `PUT /mcp/v1/catalog`                                            | Stores the relay's tool catalog and its version for the tenant                                                                                                                                                                  | 204                                                                                                                                                                                                                  |
| `POST /mcp/v1/poll` `{catalogVersion, max ≤ 32, waitMs ≤ 25000}` | Offers up to `max` `PENDING` intents of the caller's tenant under fresh tokens (`FOR UPDATE SKIP LOCKED`, so concurrent polls never share an intent); waits on `NOTIFY` when there are none; returns at once on a draining node | 200 `{tasks: [{token, key, tool, arguments, deadlineMs}]}`, possibly empty; 409 when the catalog version is stale. `key` is `<executionId>/<position>#<sequence>` – unique within the tenant, stable across recovery |
| `POST /mcp/v1/tasks/{token}/ack`                                 | `OFFERED(token) → STARTED` if the offer is current and the caller's tenant owns it; idempotent for the same token                                                                                                               | 204, or 409 – the relay must not execute (offer lapsed, call settled or cancelled, or another tenant's token)                                                                                                        |
| `POST /mcp/v1/tasks/{token}/complete` `{result \| error}`        | `STARTED(token) → DONE`; first outcome wins                                                                                                                                                                                     | 204, 409 already settled, 404 unknown or foreign                                                                                                                                                                     |

A relay acknowledges before executing, executes only after a 204, retries `ack` and `complete` until it gets an answer, and may de-duplicate by `key` across its own restarts. Tenant binding is the JWT claim on every request; request ownership is the tenant check on `ack` and `complete`; catalog invalidation is the version carried by every poll.

#### Wake-ups

Each node keeps one dedicated `LISTEN` connection on `hensu_intent` (payload: tenant), `hensu_outcome` (payload: intent id) and `hensu_runnable`. Per the `LISTEN` rule, after (re)connecting a node re-reads the state it waits on. A missed notification costs latency, never correctness: every waiter also re-reads on a 1 s safety interval. Every `NOTIFY` is issued inside the statement that makes the change, so it is delivered only if the change commits.

A fourth channel, `hensu_events`, carries execution events (`execution.started`, `tool.invoked`, …) from the node running an execution to subscribers on every node, so an event stream works wherever the LB sends it (L3). An event is data the client may miss – it is a progress view, never the record – and one that does not fit the 8000-byte payload has its longest strings cut and is marked `truncated`; the execution resource always has the full state.

## 4. Model

The protocol is specified in TLA+ (`JournaledPull.tla`, with model values in `MCJournaledPull.tla`) and checked with TLC (`TLC2 Version 2026.10.20.183001`, rev `d2e1472`, breadth-first, 7 workers). The spec and its model configurations are in [`docs/tla/`](tla/), one configuration per run below; with `tla2tools.jar` from the TLA+ releases (<https://github.com/tlaplus/tlaplus/releases>) a run is reproduced with

```bash
java -cp tla2tools.jar tlc2.TLC -workers auto -config MCJournaledPull_AllFaults.cfg MCJournaledPull.tla
```

### What the Model Contains

| Aspect                             | `JournaledPull.tla`                                                                                      |
|------------------------------------|----------------------------------------------------------------------------------------------------------|
| Nodes, executions, tenants, relays | 2, 1 or 2, 1, 1                                                                                          |
| Time                               | One DB clock `now`; TTL 2, renewal every tick, ack deadline 1, call deadline 2, dispatch deadline 3      |
| Node clocks                        | `Skew` declared and read by no guard – the point of the design                                           |
| Faults                             | Pause, node–DB partition, lost poll responses and lost ack replies, drain, abort                         |
| LB                                 | Every relay request (`Ack(n, …)`, `Complete(n, …)`) and every poll (`Offer(n, …)`) is served by any node |
| Run                                | Checkpoint, intent insert (fenced, keyed), await the outcome, finish                                     |
| Writes                             | Fenced on `claim_epoch` and `run_state`, as section 3.1                                                  |

`Tick` advances time only while every node that is up and reaches the DB has renewed on schedule. Without that guard every behaviour in which a healthy node is merely slow would count as a live steal; with it, a lease can only be lost to a fault the model names. One tenant is enough: every statement of the protocol carries `tenant_id` in its key or `WHERE` clause, nothing couples two tenants except the shared notification queue, and notifications carry no data (section 3.1). The model-turn journal is reduced to its effect on tool calls – a replayed run reaches the same key and `InsertIntent` finds the original intent – because turn replay is a deterministic function of the journal, which the unit tests and the fault-injection test check directly.

The invariants are the section 1 IDs, stated over the model's variables:

| Invariant | Property                                                                                                        |
|-----------|-----------------------------------------------------------------------------------------------------------------|
| S1        | `S1_OneRunPerClaim`                                                                                             |
| S2        | `S2_FencedHistory`: committed writes form one non-decreasing chain of epochs, none newer than the current claim |
| S3        | `S3_NoStaleIntent`, `S3_ExecutedWereJournaled`                                                                  |
| S3a       | `S3a_AtMostOnce`                                                                                                |
| S5        | `S5_NoLiveSteal`                                                                                                |
| S6        | `S6_OneOutcome`                                                                                                 |

`AllFaults` is exhaustive within its bounds (`MaxTime 4`, `MaxEpoch 2`, `MaxTokens 2`): every interleaving of a start, a pickup after expiry or drain, two offers of the one intent, lost poll responses and ack replies, a call timeout, an unavailable outcome, aborts and drains, on two nodes with one of them four ticks ahead. The two-execution models add the interference between executions that share the relay, the offer-token counter, a node's batched renewal and the deadline sweeps; the fault set is split between them, and both use symmetry over nodes and over executions. Their horizon is `MaxTime 2`, with the dispatch deadline cut to 2 ticks so that the `UNAVAILABLE` sweep falls inside it. At `MaxTime 3` the product of two executions does not finish: the pause-and-lose model was stopped after 39,655,714 distinct states (200,135,529 generated) at depth 25, with 16,950,959 states still queued and no violation; measured against one-execution models with the same faults at `MaxTime` 1 and 2, the two-execution count grows as the 1.63rd to 1.70th power of the one-execution count, which puts `MaxTime 3` at two billion distinct states or more. Two ticks are enough for each mechanism to fire: a claim expires and is picked up (TTL 2), an offer lapses and is re-offered (ack deadline 1), and a started call times out (call deadline 2); the two-execution probes below show the interference is reached. TLC's estimate of the probability that a fingerprint collision hid a state is 1.2 × 10⁻⁶ for `AllFaults`, 6.7 × 10⁻⁵ for `TwoExecs_PauseLose` and 5.4 × 10⁻³ for `TwoExecs_PartitionDrainAbort`; a second run of the last with another fingerprint polynomial (`-fp`) would lower it further.

### Non-Vacuity

A safety property is only as strong as the behaviours the model reaches. Each probe below is the negation of a situation the invariants are about, so TLC reporting it *violated* shows the situation is reachable. Each probe has its own configuration, `MCJournaledPull_Reach_<probe>.cfg`, with the bounds and faults of `AllFaults` for the one-execution probes and of `TwoExecs_PauseLose` for the two-execution probes:

| Probe                            | Model          | Situation reached                                                                                                                                                                                                                | Trace     |
|----------------------------------|----------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------|
| `Reach_ZombieRun`                | one execution  | A run still acting under a superseded epoch (partition of the holder, pickup by the other node)                                                                                                                                  | 7 states  |
| `Reach_ReofferedIntent`          | one execution  | The relay holds two offers of one intent under different tokens (offer lapsed, re-offered)                                                                                                                                       | 10 states |
| `Reach_ExecutedAfterClaimChange` | one execution  | The relay executed an intent of an execution whose claim has since moved                                                                                                                                                         | 10 states |
| `Reach_TimeoutOutcome`           | one execution  | An intent settled `TIMEOUT` while the relay had executed it and not yet completed it                                                                                                                                             | 13 states |
| `Reach_MixedRenewal`             | two executions | One node holds a live run of one execution and a superseded run of the other, so its batched renewal must extend one claim and cancel the other run (the node paused past the first claim's expiry, the other node picked it up) | 8 states  |
| `Reach_InterleavedTokens`        | two executions | The shared token counter interleaves the executions: the relay holds a lapsed and a current offer of one execution with the other execution's offer between them                                                                 | 15 states |

Traces are TLC's first counterexample with several workers, which need not be the shortest.

### What the Model Does Not Show

TLC checks safety within the bounds above; it does not check liveness, which needs unbounded time, and it does not check more than one intent per node attempt, more than two claims, every fault together with two executions, or two executions beyond two ticks. L1–L5, many concurrent executions and the unbounded behaviour are covered by the fault-injection test (section 5), which runs the implementation rather than the spec.

## 6. Rollout

The cutover is from the version whose schema ends at `V5`. It is a one-time stop-and-start, not a rolling deploy. The old version owns an execution by node id, judges staleness by heartbeat age and writes snapshots without a fence, while the new version owns it by a claim epoch that every write compares. Neither sees the other's ownership, so a mixed cluster would hold neither S1 nor S2. Nor could one last: the first new node to start applies V6, which drops the columns the old nodes checkpoint, heartbeat and sweep on, so each old node's next write fails. The relay protocol changes in the same release.

1. Stop every server node. `SIGTERM` drains nothing on the old version: a running execution keeps its `server_node_id`, which step 3 relies on.
2. Upgrade the tenants' relays to the pull protocol. Until a server answers `/mcp/v1`, a pull relay's polls fail and it retries; nothing is lost, because no intent exists yet.
3. Start the new version. Flyway applies V6: a row an old node still owned becomes `RUNNABLE`, a finished one `DONE`, any other `PAUSED`. The first pickup resumes the `RUNNABLE` executions from their last checkpoint. They have no journal yet, so this one recovery re-runs the interrupted node attempt as the old version would have – the last time that happens.

After the cutover, rolling deploys are routine (L5): a stopping node releases its claims and readiness goes down before the process exits. Future schema changes must be expand-then-contract across two releases so that adjacent versions share a schema.

No bridge for stream relays (`GET /mcp/connect`) is built. Their stream is per-node connection state, which is exactly what the design removes; a bridge would serve no invariant, and the only relay implementation is the reference client, which ships in the same change.
